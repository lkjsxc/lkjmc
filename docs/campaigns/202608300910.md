## 1. Mission

### 1.1 Primary objective

Using one exact independently verified lkjmc release and one authorized, isolated, unprivileged clone
of a healthy existing supported deployment, prove the complete disposable operator adoption and
recovery path:

> The operator can transfer and verify the exact release without rebuilding it, perform one changed
> immutable update, prove that repeating the identical update is a true no-op, survive a direct
> systemd restart and a full container restart, verify the updater-created PostgreSQL backup by
> restoring it into an isolated fresh database and crossing the daemon boundary, then interrupt a
> fresh update after the durable deployment fence exists and recover the verified previous release
> through the packaged recovery authority, all without public traffic or production mutation.

This is primarily an **external-boundary proof and narrow defect-repair campaign**. It is not a new
product-feature campaign and it is not authorization to redesign the updater. Source changes are
required only when the real supported boundary disproves a current invariant or exposes a defect that
prevents the objective.

chain:

source deliberately withdraws checkout installation and supports update of an existing deployment.

### 6.7 Restart and adoption invariants

- A direct systemd restart intentionally changes process identity but preserves release identity,
  topology, database, configuration, and listener boundaries.

- A container restart changes boot identity and may change process identifiers, but the same exact
  selected release must return through supported systemd ordering.
- Each restart requires bounded readiness, no crash loop, no orphan, no duplicate process group, fresh
  registrations/heartbeats where retained, and local protocol status.
- Service restart proof does not imply container restart proof.

- The changed update creates one fresh private transaction-consistent backup before mutation.

  daemon boot or current strongest application check all pass.
- The source database and failed restore target remain separate until acceptance.
- Restore cleanup cannot delete the source backup or source database.
- Backup creation and restore acceptance remain separate evidence states.

### 6.9 Fence, interruption, and recovery invariants

- The update writes a durable root-owned state record and effective systemd fence before ambiguous
  runtime mutation.
- The external interruption targets only the exact updater process in the disposable target.
- After interruption, the fence, state, backup, previous release, and target release remain
  inspectable.
- While fenced, automatic or manual service/container restart cannot bypass the one-use permit
  contract.
- Recovery begins by stopping and classifying surviving service-account processes.
- With an unchanged compatible migration ledger, recovery restores exact previous unit, pointer,
  plugins, release identity, systemd ownership, readiness, and local protocol status.
- With a changed or unreadable migration ledger, binary-only recovery is forbidden; service remains
  fenced until data-aware restore through the verified backup and host rollback boundary.
- Fence and permit are removed only after the recovered release independently passes acceptance.
- Failure preserves the only verified old release, target release, backup, and external rollback point.

### 6.10 Network and credential invariants

- The disposable target receives no production traffic.
- No public proxy device or public route is attached.
- Daemon HTTP, PostgreSQL, and backend listeners remain private.
- Any Velocity listener is reachable only from the explicitly bounded disposable test vantage point.
- Copied credentials remain private and are not printed, committed, or retained after clone cleanup.
- External integration side effects are blocked or disabled outside production without changing
  production credentials.
- No firewall, DNS, proxy, route, or unrelated host service is changed unless required only to remove
  accidental disposable exposure, with rollback and post-checks.

the same committed migration ledger as the baseline even though its source commit differs.

Codex must compare exact ordered migration ledgers before update, after update, after restart, in the
restored database, at interruption, and after recovery. Do not infer compatibility from the latest
migration number alone.

If a source repair requires a new migration, stop and reassess the campaign's recovery design before
implementation. A new migration is objective-critical scope expansion because it may invalidate
binary rollback and the selected post-fence recovery experiment.

### 8.2 Release cutover

The changed update performs one cutover:

1. verify baseline and target;
2. create and verify backup;
3. install target into a nonconflicting versioned root;
4. write durable state and fence;
5. stop verified owned runtime;
6. publish exact runtime files and current pointer through maintained atomic owners;
7. run migrations and classify ledger;
8. start through the bounded permit;
9. verify target;
10. remove fence/permit only after acceptance.

Do not manually copy a single binary, jar, plugin, unit, or pointer around the coordinator to “help”
the update.

### 8.3 What may be deleted

Delete only:

- operation-owned temporary artifact download and extraction state after retained evidence is secure;
- failed candidate target directories that the packaged owner classifies as unselected and safe to
  remove;
- isolated restore databases and sockets after restore acceptance;
- disposable clone, temporary snapshot, transferred credential copies, and private evidence when the
  operator has recorded final evidence and no retention need remains;
- source workarounds, duplicate tests, bypasses, or temporary compatibility code introduced by a
  rejected repair.

### 8.4 What must be retained until closure

Retain:

- exact previous release;
- exact target release;
- updater-created backup and metadata;
- host rollback snapshot or equivalent;
- release artifact identities and bounded evidence;
- source database;
- interrupted deployment state until recovery is accepted;
- first-causal failure evidence for any repair.

Never delete a production source deployment, world, database, backup, credential, snapshot, network
device, or unrelated host resource.

## 9. Failure, interruption, and recovery contract

For every material failure, record: visible result, durable state, retry semantics, cleanup owner,
diagnostics, recovery, and stop condition.

### 9.1 Artifact unavailable, expired, or mismatched

- **Visible result:** exact retrieval or verification fails nonzero.
- **Durable state:** no host mutation.
- **Retry:** retrieve another exact accepted artifact or produce a fresh exact workflow artifact under
  the current release contract.
- **Cleanup owner:** operator workspace owner removes only private partial downloads.
- **Diagnostics:** run, artifact ID/name, expected and observed size/digest, no credentials.
- **Recovery:** none; restart artifact verification.
- **Stop:** never substitute `latest`, manifest-only evidence, or a silent rebuild.

### 9.2 No authorized or isolated existing baseline

- **Visible result:** live tier is `BLOCKED` with the missing authorization, identity, capacity, or
  isolation prerequisite named.
- **Durable state:** repository and production unchanged.
- **Retry:** after a valid target or authorization exists.
- **Cleanup owner:** remove any incomplete clone owned by this campaign.
- **Diagnostics:** bounded host facts without unnecessary private identifiers.
- **Recovery:** none.
- **Stop:** do not clean-install or use production as a substitute.

### 9.3 Negative or normal preflight failure before mutation

- **Visible result:** nonzero with the failed invariant.
- **Durable state:** baseline service, database, release, plugins, unit, pointer, network, and backup
  inventory unchanged.
- **Retry:** correct the exact input or repair a demonstrated source defect, then restart from verified
  baseline.
- **Cleanup owner:** updater/operator removes only owned temporary target or backup partial state.
- **Diagnostics:** secret-free first causal error.
- **Recovery:** none if no effect crossed.
- **Stop:** any service/data mutation makes this a defect requiring source repair and baseline restore.

### 9.4 Backup creation or verification failure

- **Visible result:** update fails before fencing or service stop.
- **Durable state:** baseline remains active; no accepted backup exists.
- **Retry:** use a new nonexisting path after correcting capacity, permissions, tool compatibility, or
  database prerequisite.
- **Cleanup owner:** backup owner removes partial files only.
- **Diagnostics:** dump/list/schema/checksum failure without URL or password.
- **Recovery:** no runtime rollback required.
- **Stop:** never proceed with an unverified backup.

### 9.5 Update failure before migration-ledger change

- **Visible result:** nonzero with automatic previous-release rollback or explicit stable fenced state.
- **Durable state:** one previous release active and verified, or one fenced diagnosable state retaining
  both releases and backup.
- **Retry:** only after first cause is repaired and baseline is reverified.
- **Cleanup owner:** packaged updater/recovery owner.
- **Diagnostics:** exact state result and file/process/database observations.
- **Recovery:** packaged rollback or `recover`, not manual pointer edits.
- **Stop:** no hidden mixed release or stale permit.

### 9.6 Update failure after migration-ledger change or unreadable ledger

- **Visible result:** nonzero; service remains fenced; receipt names backup and host rollback boundary.
- **Durable state:** no binary-only rollback; source database and backup retained.
- **Retry:** only through data-aware restore with matching release identity.
- **Cleanup owner:** operator after recovered target acceptance.
- **Diagnostics:** expected and observed ledger classification, no database URL.
- **Recovery:** verified backup plus exact host snapshot/clone state.
- **Stop:** do not start old binaries against incompatible data.

### 9.7 False no-op

- **Visible result:** command may report no-op, but independent oracle detects a backup, restart,
  rewrite, pointer change, migration, fence, or state change.
- **Durable state:** preserve evidence and restore the clone baseline if necessary.
- **Retry:** only after source repair and new exact release.
- **Cleanup owner:** repair owner and packaged updater.
- **Diagnostics:** exact prohibited before/after difference.
- **Recovery:** snapshot restore or packaged recovery according to crossed effect.
- **Stop:** never accept stdout as overriding observed mutation.

### 9.8 Service or container restart failure

- **Visible result:** readiness timeout, inactive/failed systemd, crash loop, orphan, wrong release, or
  listener drift.
- **Durable state:** target release and backup retained; classify fence and process state.
- **Retry:** after diagnosis; do not loop unboundedly.
- **Cleanup owner:** systemd/container operator and packaged recovery owner.
- **Diagnostics:** bounded unit/cgroup/process/log/status evidence.
- **Recovery:** packaged recovery or exact disposable snapshot rollback.
- **Stop:** do not call a port bind or process existence readiness.

### 9.9 Isolated restore failure

- **Visible result:** checksum/list/restore/migration/query/daemon acceptance fails.
- **Durable state:** source database and original backup unchanged; failed restore target retained until
  diagnosis or safely removed.
- **Retry:** create a new fresh isolated target after correcting the cause.
- **Cleanup owner:** restore operator.
- **Diagnostics:** bounded restore/tool/schema failure without credentials or row dumps.
- **Recovery:** none for source deployment because it was not mutated.
- **Stop:** do not overwrite or rename the source database.

### 9.10 Interruption misses the intended window

- **Visible result:** update completes, interruption occurs before durable fence, or process identity is
  ambiguous.
- **Durable state:** classify the observed outcome honestly.
- **Retry:** restore exact baseline and use a safer bounded process-control sequence.
- **Cleanup owner:** disposable operator.
- **Diagnostics:** observed fence/state/process timing.
- **Recovery:** according to actual state, never by assuming interruption point.
- **Stop:** do not count an unobserved race as post-fence proof.

### 9.11 Interrupted recovery failure

- **Visible result:** `recover` fails, previous release does not verify, surviving processes remain, or
  fence/permit cleanup is incomplete.
- **Durable state:** keep service fenced, both releases, backup, state, and snapshot retained.
- **Retry:** only after exact cause and migration compatibility are known.
- **Cleanup owner:** packaged recovery and operator.
- **Diagnostics:** exact state and first failure, secret-free.
- **Recovery:** data-aware restore or disposable snapshot rollback.
- **Stop:** never delete the fence to force startup.

### 9.12 Host capacity, disk exhaustion, or manager failure

- **Visible result:** clone/snapshot/transfer/update stops truthfully.
- **Durable state:** no production mutation; partial owned clone classified.
- **Retry:** after capacity or manager health is restored.
- **Cleanup owner:** host operator removes only campaign-owned partial resources.
- **Diagnostics:** bounded capacity and manager errors.
- **Recovery:** restore/delete disposable partial state as appropriate.
- **Stop:** do not remove unrelated workloads or weaken resource isolation.
