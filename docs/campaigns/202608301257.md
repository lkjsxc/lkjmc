Visible result:

- clone/update work stops before mutation.

Visible result:

- scenario fails immediately.

Durable state:

- previous release remains selected and ready;
- no fence or partial backup is treated as valid;
- operation-owned partial files are cleaned without deleting unrelated backups.

Retry:

- only after capacity/path/root cause is corrected and a fresh backup destination is chosen.

### 8.7 Failure before publication or migration

Visible result:

- updater records the first cause;
- old release is restarted and independently verified when safe;
- if restart fails, the durable fence remains.

Retry:

- only from a fully classified state;
- do not manually remove the fence to continue.

### 8.8 Failure after publication with unchanged migration ledger

Visible result:

- packaged automatic rollback or explicit packaged recovery restores previous bytes and verifies the
  old release.

Durable state:

- receipt records rollback outcome;
- backup and target release remain available.

Retry:

- start again only from a verified baseline and fresh backup destination.

### 8.9 Changed or unreadable migration ledger

Visible result:

- service remains fenced;
- binary-only rollback is refused;
- receipt names exact backup and host rollback state required for data-aware recovery.

Recovery:

- restore matching data and release identity in an isolated or host-rollback path;
- never only repoint `current`.

### 8.10 Direct service or container restart failure

Visible result:

- distinguish systemd failure, application readiness failure, protocol failure, crash loop, orphan,
  and exposure drift.

Recovery:

- retain logs and process facts;
- stop the disposable target when safety is uncertain;
- return to the verified host snapshot before another row.

### 8.11 Interruption timing race

If the update completes before interruption:

- classify the attempt as a normal update, not interruption proof;
- restore a fresh baseline and retry with better external observation.

If interruption occurs before durable fence and prepared state:

- classify it as pre-fence interruption only;
- verify no mutation;
- restore baseline and retry.

If migration changes before interruption:

- do not force binary recovery;
- keep fenced and use data-aware recovery or restore the host snapshot;
- repeat the binary-recovery case from a clean baseline with an earlier verified interruption point.

No production test hook is added merely for timing convenience unless real evidence proves no safe
external observation mechanism exists and a narrowly guarded, non-shipping or explicitly controlled
mechanism can preserve production safety. Prefer verified process control and host observation.

### 8.12 Recovery failure

Visible result:

- fence remains;
- service remains stopped or safely classified;
- first recovery cause is preserved;
- backup, old release, target release, journal, and host rollback point remain.

Retry:

- only after verifying unchanged inputs and correcting the root cause;
- never delete or bypass the fence manually to claim success.

### 8.13 Cleanup failure after accepted state

Visible result:

- accepted runtime remains selected;
- cleanup error is reported separately.

Recovery:

- retain the valid state;
- remove only operation-owned temporary resources after identity revalidation;
- do not roll back a healthy accepted release solely because optional cleanup failed.
