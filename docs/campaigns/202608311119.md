## 1. Mission, rationale, and accepted final state

### 1.1 Primary objective

Cut the supported immutable-update and packaged-recovery path over to one Rust-owned operational
authority that validates and operates on a bounded, typed, topology-neutral Minecraft instance
inventory, without `hub` or `survival` name/count semantics and without shipped Python or shell
executables.

The affected outcome is the operator's ability to update, restart, recover, back up, restore, and
diagnose an lkjmc-managed fleet whose instance IDs and backend composition are chosen by the operator
rather than by source-code constants.

### 1.2 The bottleneck this campaign closes

The current Rust data model, PostgreSQL tables, CLI lifecycle commands, runtime launcher, and Velocity
routing code already represent arbitrary instance IDs and several server kinds. The accepted packaged
operations path does not. Its preflight, credential enumeration, EULA checks, plugin installation,
readiness checks, status checks, fixed ports, and default routing encode exactly one `proxy`, one
`hub`, and one `survival`. The release also ships privileged Python and shell programs as product
artifacts.

That mismatch makes the generic control-plane surface misleading. Merely rerunning the blocked Docker
matrix would prove the old fixed-topology Python/shell release rather than the product the user now
wants. Adding more instance features before replacing that authority would create another parallel
system.

### 1.4 Why this campaign won

Four credible candidates were compared.

#### Candidate A — unblock and rerun the existing Docker recovery matrix

This is the smallest path to higher live evidence. It lost because it would validate an exact release
whose privileged authority is Python/shell and whose accepted topology is exactly
`proxy`/`hub`/`survival`. The user's new product and language policy makes that evidence stale before
execution. The predecessor's resource-capacity work remains useful input, but its old target is not
worth promoting.

#### Candidate B — Rust-owned topology-neutral update and recovery cutover

This campaign wins because it removes the primary contradiction at the release boundary, preserves
the strongest safety work already implemented, contracts six or more shipped operational programs
into one typed authority, and makes later live recovery and fleet proofs meaningful. It is a strict
prerequisite for trustworthy supported-host work.

#### Candidate C — complete a generic multi-instance create/start/stop operator journey

This has immediate operator value and aligns closely with the user's one-for-all direction. It is
deferred because the deployed update/recovery path would still reject or misclassify the resulting
fleet, leaving two incompatible product truths.

#### Candidate D — contract the broad command and gameplay surface

The repository exposes many domains beyond the proven credible core. Removing fake, denied, or
unmaintained domains is high-value architectural contraction. It is deferred because it does not
repair the packaged authority that protects releases and data.

#### Candidate E — real-player command and transfer acceptance

This is the strongest player-facing alternative. It is deferred because player evidence should bind
to the intended release and topology model, not the superseded fixed-topology package.

- A topology whose current readiness or plugin contract is unsupported fails before service

### 5.4 EULA invariants

Use one versioned, exact, root-owned, non-symlink policy record under the canonical private
configuration root. The active checkout may retain the current marker path if it remains sound.

The record must:

- state schema version and acceptance;
- have exact private ownership and mode;
- be parsed without shell interpretation;
- be written atomically and durably;
- be independently reread and verified;
- be referenced in a bounded operation/audit receipt;
- never contain secrets.

Instance creation and planning persist valid typed desired state without a caller-supplied legal

Remove per-command legal-confirmation fields and fixed-backend fallback checks. Do not delete an
operator-owned valid EULA file merely because an instance is stopped or an update is rolled back.

### 5.5 Rust operations authority

The Rust binary must expose direct typed subcommands rather than dispatching on arbitrary strings.
Recommended groups:

- `release verify`;
- `artifacts install`;
- `deploy update`;
- `deploy recover`;
- `database backup`;
- `database restore`;
- `fence check`;
- `bootstrap after-start`;
- `diagnose`.

The active checkout may choose a smaller public command shape if every maintained systemd, operator,
and recovery consumer is served and there is still one authority.

Privilege checks are subcommand-specific. A root-required command fails before mutation when not
root. A service-user command rejects root-only state it does not need. Shared parsing and verification
may be unprivileged.

The binary must use:

- explicit bounded arguments;
- structured internal types;
- stable operation IDs;
- one global deployment lock;
- a durable journal/fence for interrupted changed updates;
- no-follow and atomic filesystem operations;
- exact manifest and artifact digest checks;
- bounded subprocess execution without a shell;
- safe environment construction;
- redacted diagnostics;
- deterministic receipts.

### 5.6 Update state machine

Use an explicit state machine equivalent in behavior to:

1. `preflight`;
2. `no-op` or `backup-required`;
3. `backup-verified`;
4. `fenced`;
5. `service-stopped`;
6. `artifacts-staged`;
7. `migration-classified`;
8. `activated`;
9. `service-starting`;
10. `post-start-verifying`;
11. `accepted`;
12. `rolled-back`;
13. `restore-required`;
14. `recovery-blocked`.

Exact names are implementation latitude; semantic distinctions are not.

The durable record must bind:

- operation ID;
- source and target release identities;
- manifest digest;
- prior release root;
- prior unit/plugin/artifact identities;
- migration ledger before and after;
- backup closure;
- rollback/snapshot assertion supplied by the operator;
- current phase;
- first causal failure;
- recovery decision.

Retry with the same operation identity is idempotent at real external effects. A conflicting operation
is rejected while the lock or durable unresolved fence exists.

### 5.7 Exact no-op

A target is a no-op only when the externally anchored target identity and complete installed release
identity are already equal and current state is not fenced or inconsistent.

A no-op:

- performs read-only validation;
- does not create a backup;
- does not stop or restart the service;
- does not run migrations;
- does not rewrite the unit, plugins, pointer, policy, or artifacts;
- does not rotate credentials;
- returns a bounded receipt proving why it was a no-op.

Topology drift, corrupted current bytes, stale fence, or mismatched manifest is not a no-op.

### 5.8 Changed update, rollback, and recovery

Before stopping service:

- verify exact current and target release identities;
- validate the dynamic fleet and required readiness;
- verify immutable assets and installed plugins by inventory;
- verify the EULA policy and all required materialized files;
- obtain the global lock;
- create and independently verify a new private PostgreSQL backup;
- write and fsync the durable journal and fence.

After fencing:

- stop the complete verified systemd cgroup;
- stage artifacts on the target filesystem;
- atomically publish versioned files;
- install the unit and plugins derived from inventory;
- run ordered migrations while stopped;
- activate the target once;
- grant only the one-use fenced start permission;
- start and verify through systemd;
- compare exact build identity and dynamic required instance state;
- remove permit and fence only after acceptance.

Before any migration-ledger change, failure may restore the exact prior unit, pointer, plugins, and
artifacts and verify the previous release.

After a changed or unreadable ledger, do not perform binary-only rollback. Keep service fenced, retain
all recovery inputs, and report the matching backup and release identities required for data-aware
recovery.

`deploy recover` must be the exact packaged Rust program from an anchored release. It stops any
running service first, validates the durable journal, and either restores the safe pre-transition
state or remains fenced with a precise blocker.

### 5.9 PostgreSQL backup and restore

Backup and restore remain separate effects.

A backup closure must include:

- private dump bytes;
- exact checksum closure;
- server version;
- source release identity;
- migration marker;
- schema identity;
- creation identity and timestamp bounds;
- independent `pg_restore --list` or equivalent structural inspection.

The Rust authority invokes PostgreSQL tools through fixed validated paths and bounded environments.
It does not parse a database URL through shell semantics or log credentials.

Restore acceptance requires a new isolated target, checksum and metadata verification, schema and
migration agreement, and explicit release compatibility. Restoring over the live database is outside
the minimum campaign unless an existing maintained command already does so safely and the campaign
can test it without external risk.

### 5.10 Systemd and process invariants

- The canonical unit invokes the Rust fence check and Rust post-start bootstrap.
- No `ExecStartPre`, `ExecStartPost`, recovery, or operator instruction points to a deleted script.
- The fence survives service and container restart.
- A one-use permission cannot be replayed.
- Service start without a valid permission while fenced fails closed.
- Process and cgroup identity are independently observed.
- Post-start bootstrap enumerates the configured fleet rather than a fixed list.
- Startup preserves intentionally stopped instances.
- Readiness is bounded by kind/integration contract.
- A failed post-start check leaves evidence and follows the update rollback classification; it does
  not clear the fence merely because the daemon process exists.

### 5.11 Release and installed-artifact invariants

- The release inventory is explicit and exact.
- The new Rust binary has embedded source identity.
- Removed executable names are absent from source inventory, release source, manifest, archive,
  installed tree, systemd unit, docs, and CI.
- Release construction uses the exact clean commit and fresh Rust/Java outputs.
- The existing independently verified manifest/archive model may be retained when still sound.
- Installed artifacts are root-owned, non-writable by untrusted principals, and verified by size and
  digest.
- Configuration, secrets, worlds, logs, backups, server jars, and runtime state remain outside
  immutable release bytes.
- Runtime services do not compile source, invoke Gradle/Cargo, or resolve mutable artifact channels.

## 8. Failure, interruption, retry, and recovery

For every material failure record visible result, durable state, retry semantics, cleanup owner,
diagnostics, recovery action, and stop condition.

### 8.1 Input and authorization failures

Malformed manifest, unsafe path, wrong owner/mode, digest mismatch, wrong source commit, unsupported
schema, unknown instance kind, duplicate ID/socket, invalid route, missing asset, unsupported
readiness, missing EULA policy, or insufficient privilege fails before service mutation.

An unauthorized or ambiguous target is nonretryable until corrected.

### 8.2 Lock and concurrency

A second deployment operation fails without mutation while the global lock is held. Stale durable
operation state is not silently discarded. Recovery must classify it using exact identities.

### 8.3 Backup failures

Failed dump, timeout, disk exhaustion, malformed metadata, checksum mismatch, structural inspection
failure, or existing destination prevents fencing and service stop. Partial operation-owned backup
state is removed only when identity proves ownership; valid prior backups remain.

### 8.4 Artifact failures

Interrupted copy, fsync failure, digest mismatch, unsafe link, target conflict, permission failure, or
disk exhaustion before publication preserves the previous valid installed tree. Cleanup failure after
a durable accepted publication does not delete both valid states.

### 8.5 Service and process failures

Failed stop, surviving child, stale process identity, PID reuse, systemd timeout, rejected permit,
failed start, crash loop, or post-start readiness failure remains visible. The fence is not cleared
because a PID or socket exists.

### 8.6 Database transition failures

Before migration-ledger change, restore the safe prior binary/artifact state where the prior database
remains compatible.

After changed or unreadable ledger, stop, remain fenced, retain both releases and backup, and report
data-aware restore requirements. Do not guess compatibility.

### 8.7 EULA failures

Missing third-party operator policy, unsafe marker, ambiguous instance directory, EULA write failure,
or verification mismatch leaves the affected instance stopped. Do not generate a success receipt.

For repository-owner-controlled disposable or authorized environments, absence of the marker is
repairable by creating the exact authorized policy record; it is not a reason to ask this user again.

### 8.8 Interruption and restart

A process, service, container, or host restart during changed update must encounter durable fenced
state. Only an exact one-use permission permits the updater's verification start. Recovery is
idempotent and refuses a target whose journal, releases, database ledger, or backup identity differs.

### 8.9 Optional live-environment blocker

Insufficient project-scoped capacity, unavailable systemd, unavailable immutable server assets, or
unsafe Docker isolation is `BLOCKED`. Complete independent source, deterministic, PostgreSQL,
packaging, and artifact work and report the exact external blocker. Do not mutate shared Docker or
production state to manufacture a pass.
