## 1. Mission, bottleneck, and accepted final state

### 1.1 Primary objective

For one exact final source commit and one exact independently retrieved release, make a fresh,
authorized, unprivileged Linux system container installable through one Rust-owned first-install
operation, then prove that the resulting topology-neutral lkjmc network reaches truthful systemd,
PostgreSQL, operator, restart, backup/restore, and Minecraft status-protocol acceptance without a
source checkout, build toolchain, Python or shell product authority, disabled-only executable, or
public production cutover.

The observable final outcome is:

> Starting from a named fresh unprivileged Incus or LXD system container whose base operating-system
> substrate already provides systemd, a compatible Java runtime, and PostgreSQL, an operator supplies
> one exact verified lkjmc release plus one exact immutable installation-input closure, invokes one
> packaged Rust first-install authority, and obtains a private, restart-stable lkjmc deployment with
> one configured Velocity entrypoint and one configured backend using noncanonical instance IDs. The
> operator can observe exact release identity, converged durable state, bounded diagnosis, a real
> local Minecraft status response, and an independently verified isolated PostgreSQL restore. A
> repeated identical install is an exact read-only no-op.

This campaign closes **first adoption of an exact release on the supported container shape**. It does
not claim real-player login or transfer, public internet reachability, production adoption, a changed
release update, rollback across incompatible migrations, durable public release publication, or full
retirement of every historical non-core data domain.

### 1.2 The bottleneck this campaign closes

The predecessor replaced fixed-topology Python and shell operational authority with the Rust
`lkjmc-ops` path and produced an exact release that GitHub retained and independently reconsumed. The
current operations documentation nevertheless says clean-host installation is unsupported. The
maintained updater assumes that PostgreSQL, identities, configuration, immutable server assets,
credentials, paths, and systemd already exist. Therefore an operator still has no supported path from
an accepted release artifact to a fresh running lkjmc system.

The release boundary also contains one concrete truth defect: the inspected inventory includes
`lkjmc-discord`, while that executable reports that Discord startup and registration are withdrawn.
Installing the current payload would canonize a disabled-only component that is absent from the
credible core. Removing that executable and its direct release consumers is a strict dependency of a
truthful first-install campaign, not a new Discord feature campaign.

## 2. Candidate comparison and selection rationale

### 2.1 Candidate A — evidence-only closure of the predecessor

The remote branch and workflow now provide stronger evidence than the stale active ledger: the exact
Rust cutover commit was pushed, its required workflow passed, an exact release artifact was retained,
and a separate consumer verified it. Updating the ledger is necessary, but a campaign limited to that
correction would leave the release unusable on a fresh supported target. This work is absorbed as the
first reconciliation slice rather than selected as the whole campaign.

### 2.2 Candidate B — rerun the changed-update and recovery matrix on the Rust release

This is the strongest rejected alternative. It would prove critical update, interruption, fence,
restart, backup, restore, and recovery behavior against the new topology-neutral Rust authority. It
is deferred because the repository still lacks a maintained way to create the first accepted
installation. Requiring another test-only bootstrap fixture would repeat the split between product
truth and proof setup. Once this campaign produces one supported fresh installation, a subsequent
changed-update campaign can start from a product-created baseline and focus narrowly on update and
recovery semantics.

### 2.3 Candidate C — Rust-owned fresh supported-container installation

This campaign wins. It closes the first missing operator journey from accepted release bytes to a
running supported system, reuses the existing secure release installer rather than replacing it,
removes one known disabled release component, establishes the baseline required by later update and
player campaigns, and ends in one independently observable state. The product boundary is kept
narrow by treating container creation and operating-system package preparation as external proof
infrastructure rather than turning lkjmc into a general provisioner.

### 2.4 Candidate D — close a real-player `/lkjmc status` and transfer journey

This has the most direct player value. It remains deferred because a real-player proof should consume
a reproducible accepted installation rather than an ad hoc manually assembled host. It also requires
an online player identity and same-player arrival oracle that are unnecessary for first-install
acceptance.

### 2.5 Candidate E — broad surface contraction or durable GitHub Release publication

The repository still contains broad historical command, product, Discord, economy, and gameplay
surfaces, and the current artifact is retained only for a bounded workflow lifetime rather than as a
GitHub Release. Both are high-value later campaigns. A broad contraction would make the install
campaign too large, while publication before fresh-install acceptance would promote bytes whose
supported adoption path is still unknown. This campaign removes only the disabled executable that
would otherwise be installed and defers the wider audits.

### 2.6 Why the selected scope is dependency-closed

The objective has one final state: a fresh exact release becomes an accepted private supported-host
installation. Release contraction, first-install state, PostgreSQL initialization, assets,
credentials, EULA state, systemd activation, restart, backup/restore, artifact verification, and
supported-container observation are included because each is required to claim that final state.
Changed update, real-player transfer, production exposure, broad gameplay cleanup, signing, and
public release publication can all be deferred without leaving two first-install authorities or a
partially accepted installation.

## 6. Authority model, target design, and invariants

### 6.1 Semantic authorities

- The governing campaign owns the selected final objective, not runtime behavior.
- Root `AGENTS.md` owns durable repository policy.
- One versioned first-install input owns requested release identity, canonical configuration input,
  immutable asset closure, service/PostgreSQL target contract, and operation identity.
- The canonical typed fleet configuration owns instances, listeners, routes, assets, integrations,
  desired states, readiness, and public-entry selection.
- The release inventory and independently generated manifest own immutable release content.
- The runtime-asset descriptor owns exact external Minecraft/Velocity bytes used by the install.
- The existing root-owned EULA policy owns repository-owner consent in authorized environments.

No installer-only copy of instance kinds, topology rules, listener semantics, plugin applicability,
readiness, or EULA applicability may become a second authority.

### 6.2 Persisted authorities

- PostgreSQL owns durable fleet and operation facts after schema initialization.
- The first-install journal owns resumable privileged-operation phase and input binding.
- Installed release identity owns the exact selected release root and manifest digest.
- Secret files own credential values; PostgreSQL or configuration may reference identity/path but must
  not duplicate plaintext secrets.
- Configuration files own the installed semantic input; generated runtime files remain generated
  state.

### 6.3 Generated authorities

- Existing canonical generators own Velocity, backend, plugin, and runtime configuration.
- The release builder owns release assembly from the independent inventory.
- The manifest/archive owners derive exact content independently.
- Systemd unit and drop-in are immutable release inputs; installed copies must match their accepted
  bytes.

Generated output is not semantic intent and may not be hand-edited to make live proof pass.

### 6.4 Observed-runtime and external authorities

- systemd owns service supervision state;
- process, cgroup, executable, and start-time observation own live process identity;
- PostgreSQL connections and direct queries own database availability and schema observation;
- plugin heartbeat and Velocity status own configured component readiness;
- an independent Minecraft protocol client owns status-protocol observation;
- Incus/LXD owns container identity and restart observation;
- the host network and external vantage point own exposure truth;
- GitHub Actions and independently downloaded bytes own remote artifact retention/retrieval evidence.

### 6.5 First-install operation contract

The operation must have these behavioral properties even if local names differ:

- **Plan/preflight:** parse and validate all inputs; anchor release and assets; inspect substrate,
  identities, paths, PostgreSQL, listeners, services, and capacity; make no product-state mutation.
- **Prepared:** acquire the global lock; create and fsync the durable journal before the first effect.
- **Identity and root preparation:** create or validate exact dedicated identity and private roots.
- **Credential preparation:** generate, atomically publish, and independently re-read scoped secrets.
- **Database initialization:** create exact role/database where absent, apply ordered migrations, and
  verify migration identity.
- **Release and asset publication:** use existing secure owners to install immutable release and
  runtime assets into versioned or content-addressed roots.
- **Configuration and durable fleet initialization:** atomically install semantic configuration and
  reconcile/persist through existing owners.
- **Consent materialization:** create/validate the authorized host policy and exact per-instance EULA
  state.
- **Service publication:** install exact unit/drop-in, reload systemd, and enable only after all prior
  state is verified.
- **Activation and acceptance:** start through systemd, run packaged post-start checks, operator
  status, protocol status, and independent state inspection.
- **Accepted:** fsync a bounded final receipt and mark the operation accepted only after every required
  oracle passes.

A journal phase is not proof that its effect succeeded. On resume, independently inspect the effect
before advancing. Input changes under the same operation UUID are rejected.

### 6.6 Authentication and authorization

- First install is a root-required `lkjmc-ops` operation.
- Root authority is limited to application identity, lkjmc-owned roots, local PostgreSQL bootstrap,
  exact release/assets, systemd publication, service lifecycle, EULA policy, and bounded proof needed
  by this objective.
- The general `lkjmc` CLI remains unprivileged and must not gain hidden root mutation.
- The service runs as the dedicated unprivileged identity.
- PostgreSQL administrative capability is used only during bounded initialization and restore; the
  runtime receives only least privilege.
- No network caller, configuration field, or environment variable may assert an identity that the OS,
  PostgreSQL, Velocity, or platform can derive authoritatively.

### 6.7 Secret invariants

- Generate secrets only after every nonsecret preflight that can fail early.
- Use the operating-system cryptographic random source.
- Write through private temporary files, no-follow validation, fsync, atomic rename, and independent
  re-read.
- Apply least-privileged owner/group/mode and validate ancestry.
- Never place secrets in command-line process listings when a protected file or descriptor is
  practical.
- Never return a secret value in structured output.
- Redact database URLs, tokens, forwarding secrets, plugin credentials, and authorization headers.
- On rollback, delete only operation-owned unaccepted secret files whose exact identity is known.
- On accepted no-op, do not rotate or rewrite secrets.

### 6.8 Database invariants

- Fresh initialization uses committed migrations in order; released migrations are never edited.
- Role, database, schema, migration ledger, and expected application identity are inspected before
  mutation and after completion.
- Multi-step durable changes are transactional where possible.
- Slow filesystem, systemd, asset, or process effects do not occur while holding an unjustified
  database transaction.
- A database conflict, timeout, or incompatible schema leaves explicit journal state and a safe retry
  or stop condition.
- Failed unaccepted fresh state may be dropped only when exact operation ownership is independently
  proved; otherwise preserve and fence it.
- Backups are private, transaction-consistent, checksummed, metadata-bound, and tied to exact source
  and migration identity.
- Restore uses a fresh isolated target and does not overwrite the accepted source database.

### 6.9 Release and asset invariants

- The exact release comes from a clean final commit and an independently verified retained artifact.
- Installer input is not trusted merely because it arrived from GitHub; archive, manifest, sidecar,
  modes, file set, embedded identity, and secret boundary are reverified.
- Runtime asset resolution occurs before installation and produces immutable identity. The installed
  service never resolves mutable catalogues.
- Installation uses private staging and atomic publication.
- Installed release, installed runtime asset, generated configuration, and selected current pointer
  are independently inspectable.
- No disabled-only executable, obsolete alias, wrapper, or unmaintained unit is present in the final
  release or installed tree.

### 6.10 Process, readiness, and restart invariants

- systemd start success is not application readiness.
- Process identity resists stale PID and PID reuse and is tied to expected executable/cgroup/start
  information.
- Desired state, process state, component readiness, and player-facing readiness remain separate.
- Every desired-running instance uses its configured supported readiness contract.
- Intentionally stopped instances are preserved and are not required to be ready.
- Post-start acceptance verifies the complete configured fleet and exact release, not only the
  selected listener.
- Startup, service restart, and container restart each have bounded deadlines and separate evidence.
- Failure leaves useful bounded diagnostics, no uncontrolled crash loop, and no orphan process group.

### 6.11 Network invariants

- The chosen proof topology uses typed configuration to identify the Velocity entrypoint.
- Backend, PostgreSQL, daemon, management, and credential boundaries remain private.
- No public host port, firewall, DNS, reverse proxy, or production traffic mutation occurs.
- A container-private protocol-client reachability test does not imply public reachability.
- Listener conflicts are detected before service publication.
- Independent inspection compares configured bind addresses with actual listeners from container and
  host vantage points.

### 6.12 Unsupported behavior

Fail explicitly rather than approximating support when:

- the base substrate is incompatible;
- the target is not fresh, exact accepted, or safely resumable;
- an asset or release identity is mutable, missing, expired, corrupt, or unverifiable;
- a configured active kind lacks a supported readiness or EULA contract;
- a path, identity, database, service, process, listener, or manager target is ambiguous;
- capacity is insufficient;
- required systemd isolation cannot be applied;
- secret publication cannot meet ownership/mode requirements;
- the supported Incus/LXD boundary is unavailable.

## 9. Failure, interruption, retry, and recovery semantics

For every material case below, define a visible structured result, durable journal state, retry rule,
cleanup owner, diagnostics, recovery action, and stop condition.

### 9.1 Input and identity failures

Cover:

- malformed, unknown, duplicate, oversized, or unsupported install input;
- missing or invalid operation UUID;
- wrong release commit or manifest digest;
- expired/missing artifact and wrong outer or inner identity;
- corrupt archive, traversal, link, special file, duplicate member, wrong mode, or unexpected file;
- wrong asset kind/version/size/digest;
- configuration/schema error;
- duplicate IDs, listeners, sockets, routes, or assets;
- unsupported active kind/readiness/integration;
- changed inputs under a reused operation UUID.

These fail before effect execution whenever possible. Do not create a journal merely to record an
input that cannot be safely parsed or anchored.

### 9.2 Substrate and capacity failures

Cover:

- not root;
- systemd not PID 1 or required unit operation unavailable;
- incompatible Java/PostgreSQL/tool version;
- missing fixed utility or unsafe utility path;
- unsupported filesystem behavior;
- insufficient disk, memory, process, or file-descriptor capacity;
- existing listener conflict;
- non-unprivileged or unsafe container boundary;
- unavailable/ambiguous Incus/LXD target.

Fail before lkjmc state mutation. External environment preparation may correct the substrate; the
product installer must not silently install arbitrary packages or weaken isolation.

### 9.3 Existing-state conflicts

Cover:

- user/group name exists with wrong identity or policy;
- install/config/data/log/backup/runtime root exists with unexpected type, owner, mode, content, or
  ancestry;
- service unit exists with different bytes;
- PostgreSQL role/database/schema exists without exact accepted/resumable identity;
- secret file exists but is not exact accepted state;
- release/current pointer or asset root is mixed or ambiguous;
- service/process/listener already exists outside accepted state;
- stale journal, fence, permit, or stage from another operation.

Do not adopt or delete these. Return an actionable conflict and the independently observed facts.

### 9.4 Filesystem and secret failures

Cover:

- partial write;
- rename/fsync failure;
- disk exhaustion;
- symlink race;
- permission/ownership failure;
- interrupted release or asset publication;
- cleanup failure after a later state is already accepted.

Preserve the first causal error. Clean only exact operation-owned staging. Never delete the prior
valid state because cleanup of the new accepted state failed.

### 9.5 PostgreSQL failures

Cover:

- administrative connection failure;
- role/database creation conflict;
- migration failure;
- incompatible or altered migration ledger;
- lock conflict, timeout, pool exhaustion, or server restart;
- backup destination conflict;
- backup corruption or age/identity mismatch;
- restore target conflict or restore failure.

A failed fresh unaccepted database may be removed only when exact operation ownership and absence of
external consumers are proven. Otherwise preserve it and stop. Do not hold transactions across slow
host effects. Do not call a completed SQL transaction an accepted install.

### 9.6 Service and readiness failures

Cover:

- unit publication or `daemon-reload` failure;
- enable/start/stop timeout;
- daemon crash;
- stale PID/PID reuse;
- orphan child/process group;
- plugin load or heartbeat failure;
- backend or Velocity readiness timeout;
- PostgreSQL divergence;
- protocol status failure;
- crash loop;
- container restart during activation.

Stop the verified owned service group when safe. Keep or create the fence before an ordinary restart
could expose partial state. Do not remove the fence until exact installed state and every required
acceptance oracle pass.

### 9.7 Cancellation and interruption

Inject bounded interruption after representative durable boundaries, including:

- journal creation;
- identity/root creation;
- credential publication;
- database creation or migration;
- release staging;
- release publication;
- asset publication;
- unit publication;
- enablement;
- service start;
- before final acceptance receipt.

On restart or replay:

- verify journal and every observed effect independently;
- reject changed inputs;
- resume forward when safe;
- roll back only exact operation-owned unaccepted effects when safe;
- otherwise remain fenced and report the precise manual/exact recovery requirement;
- never mark accepted merely because a late phase name was persisted.

### 9.8 Exact no-op

Both first-install replay and same-release updater no-op must be independently fingerprinted.
Relevant files, secrets, database ledger, process identities, service timestamps, unit bytes, release
pointer, asset bytes, EULA files, backups, and journals must prove that no forbidden mutation occurred.
A diverged target is an error, not a no-op.
