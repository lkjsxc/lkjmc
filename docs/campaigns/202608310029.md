## 1. Mission, rationale, and accepted final state

### 1.1 Primary objective

Create and execute one self-contained, bounded, non-production Docker systemd acceptance lab that
consumes exact immutable lkjmc release artifacts and real immutable Minecraft runtime inputs, then:

> install a verified baseline release into a fresh canonical-path systemd/PostgreSQL deployment;
> update it through the target release's packaged deployer; prove exact no-op behavior; survive a
> direct systemd restart and a full Docker-container restart; restore the updater-created PostgreSQL
> backup into a fresh isolated database and cross the application boundary; interrupt a separate
> fresh update after the durable fence exists; prove ordinary starts remain blocked; and recover the
> verified baseline through the target release's packaged recovery authority.

The lab must use real systemd as PID 1, real PostgreSQL, the actual packaged Rust binaries and JVM
plugins, real Velocity and backend server processes, real plugin readiness, and a real Minecraft
status-protocol observation. It must publish no host player port, mutate no home server or production
state, fabricate no legal consent, add no product test bypass, and claim no stronger evidence than it
actually observes.

This is an **external integration, operator-recovery, and reusable proof-infrastructure campaign**.
It is not a clean-installer campaign, production rollout, real-player campaign, command-surface
redesign, or declaration that Docker replaces the supported Incus/LXD system-container path.

### 1.2 Affected outcome and bottleneck

The affected party is the lkjmc operator and the future coding agent that must decide whether an exact
release can be adopted and recovered without making production the first realistic test environment.

The current repository already has strong source, deterministic test, Compose verification, release
construction, artifact retention, independent artifact reconsumption, backup/restore, and deployer
state-machine work. The remaining credibility gap is that the packaged deployment path still has no
committed fresh observation across real systemd, real PostgreSQL, real process ownership, real
Minecraft readiness, restart, interruption, and recovery. The previous campaign attempted to close
that boundary on an unprivileged Incus/LXD clone and stopped before host access.

The user's newly prepared Docker development environment can close a large and durable portion of
that gap without touching production. Docker is not evidence for Incus-specific isolation, host-owned
snapshots, public exposure, real-player behavior, or production behavior, but a carefully bounded
systemd container can independently exercise the packaged updater and recovery state machine against
real local effects.

### 1.3 Why this campaign won

This campaign was selected over the strongest alternatives because it attacks the active bottleneck,
reuses the accepted exact-release chain, and can end in one coherent reusable proof boundary:

- **Directly resume the Incus/LXD campaign:** stronger when authenticated host management is
  available, but the last committed state proves that prerequisite was absent. Docker availability
  does not imply an Incus remote, safe clone target, or production-like traffic boundary. Keep this as
  the highest-priority deferred external tier rather than blocking all local progress on it.
- **Contract the overbroad command and generated-contract surface:** architecturally valuable and
  fully deterministic, but it would open a different product campaign, make the accepted release
  candidate stale, and leave the current adoption/recovery bottleneck unresolved.
- **Close the real `/lkjmc` player journey:** direct player value, but downstream of trustworthy
  release adoption and additionally dependent on explicit EULA consent, protocol-client work, and
  ultimately a real player identity. This campaign may observe only the status protocol needed by the
  updater.
- **Build a clean supported-host installer:** too broad. The repository explicitly withdrew the old
  clean installer, and Docker fixture construction must not silently revive it as a supported product
  path.
- **Rerun the existing Compose verifier only:** useful revalidation but no new confidence about
  systemd, packaged update, restart, interruption, or recovery.

### 4.7 Restart invariants

- A service restart targets only `lkjmc-daemon.service` and its owned process group.
- A Docker-container restart is performed by the host-side driver against the exact labeled container.
- Restart success requires PostgreSQL, systemd, daemon, proxy, two backends, plugin heartbeats,
  readiness, target identity, and listener boundaries.
- A normal restart must not create an updater fence or start permit.
- A fenced restart must not bypass the packaged `ExecStartPre` guard.
- Docker restart is not an Incus/system-container reboot claim.

### 4.8 Backup and restore invariants

- The update-created backup is the restore input; do not create a different convenience dump for the
  acceptance row.
- Verify dump, metadata, sidecar, checksum, manifest, server/tool major, source commit, migration

- Restore into a fresh database target with no user relations and no shared writable source volume.
- Do not overwrite or rename the source database into the restore target.
- Apply committed migrations after restore according to the current owner contract.
- Cross the application boundary with the actual target daemon and direct PostgreSQL observations.
- Retain the original backup until every restore and recovery row is accepted.

### 4.9 Interruption and recovery invariants

- The external watcher identifies the exact updater process by PID, start time, executable, cgroup,
  and command arguments without retaining secrets.
- It observes the regular fence and matching prepared state before stopping the updater.
- It verifies the migration ledger still equals the recorded pre-update value.
- It sends `SIGSTOP` or another bounded freeze before the final kill when needed to close the race.
- It never kills systemd, PostgreSQL, the Docker daemon, or an unrelated process.
- A missed or ambiguous interruption window invalidates the scenario.
- Ordinary starts and container restart remain fenced.
- Packaged recovery is anchored to the exact target release and separately supplied manifest digest.
- Recovery may restore the baseline binaries only when the migration ledger is unchanged.
- A changed or unreadable ledger leaves the service fenced and requires data-aware restore.

### 4.10 Network and secret invariants

- Publish no host port.
- Use no host network or public route.
- Backend listeners remain loopback inside the systemd host.
- Velocity may bind the fixed in-container address required by preflight, but Docker inspection must
  show no published host endpoint.
- External integrations not required by the objective remain disabled.
- Generate unique secrets per scenario.
- Do not print secret values in command lines where process inspection or logs would retain them.
- Redact database URLs, tokens, forwarding secrets, plugin credentials, authorization headers, and
  cookies.
- Evidence and logs use private modes.

The canonical result must include:

- schema version and scenario result;
- repository, implementation commit, evidence checkpoint commit when different, and remote relation;
- baseline and target release identities;
- workflow run/attempt and artifact identities where applicable;
- image and package identities;
- immutable server-asset identities;
- Docker engine mode, cgroup mode, capability boundary, and architecture;
- explicit statement that EULA acceptance was supplied, without retaining private consent material;
- project, container, network, volume, and rollback-point identities;
- exact commands, start/end times, exit codes, and timeouts;
- before/after fingerprints;
- systemd, process, PostgreSQL, migration, backup, pointer, plugin, listener, heartbeat, and protocol
  observations;
- all `PASS`, `FAILED`, `BLOCKED`, `SKIPPED`, and `NOT RUN` rows;
- cleanup result;
- a checksum/size index equal to retained regular files;
- redaction and secret-scan result;
- unsupported evidence tiers.

Evidence must be bounded, private, deterministic where applicable, and tied to exact final identities.

## 7. Failure, interruption, retry, and recovery semantics

### 7.1 Docker or systemd prerequisite failure

- **Visible result:** `BLOCKED` with the exact unavailable capability or unsafe required privilege.
- **Durable state:** no product fixture; only bounded preflight evidence.
- **Retry:** after Docker/cgroup configuration changes, rerun from preflight.
- **Cleanup owner:** the driver removes any uniquely labeled partial resource.
- **Stop condition:** do not substitute fake systemd or rootful privileged mode.

### 7.2 Missing legal consent

- **Visible result:** live Minecraft rows and campaign acceptance are `BLOCKED`.
- **Durable state:** no EULA marker and no started Minecraft server.
- **Retry:** only after explicit operator consent is supplied through the maintained gate.
- **Cleanup:** remove any pre-EULA project resources.
- **Stop condition:** do not infer consent from Docker availability, historical state, or repository
  text.

### 7.3 Missing, expired, or invalid release artifact

- **Visible result:** fail before runtime mutation.
- **Durable state:** retain bounded artifact metadata and mismatch evidence; do not retain untrusted
  extracted content as accepted input.
- **Retry:** re-download the exact artifact, use the explicitly labeled clean-build fallback for the
  baseline, or produce a new target artifact from a green final implementation commit.
- **Stop condition:** never silently rebuild and call it the retained artifact.

### 7.4 Asset or image integrity failure

- **Visible result:** fail before EULA marker, service start, or update.
- **Durable state:** private rejected cache may be deleted after retaining digest/size diagnostics.
- **Retry:** reacquire only from the authoritative source and reverify.
- **Stop condition:** no mutable or cached filename is accepted without digest agreement.

### 7.5 Baseline fixture failure

- **Visible result:** scenario `FAILED` or `BLOCKED`; no update attempt.
- **Durable state:** retain bounded systemd/PostgreSQL/process diagnostics and exact input identities.
- **Retry:** repair the fixture or product defect, destroy the project, and recreate from empty state.
- **Stop condition:** an unhealthy baseline cannot be normalized into acceptance.

### 7.6 Expected negative preflight

- **Visible result:** the deployer exits nonzero with the expected safe class.
- **Durable state:** before/after fingerprints remain equal.
- **Retry:** not needed when the expected class and no-effect oracle pass.
- **Failure:** any backup, fence, stop, pointer, migration, publication, or journal effect fails the
  row.

### 7.7 Changed-update failure

- **Before migration change:** preserve exact error, fence/journal/backup state, verify the packaged
  automatic behavior, and diagnose. Recreate from a fresh baseline before retry.
- **After migration change or unreadable ledger:** do not force binary rollback. Preserve fence,
  backup, rollback point, both releases, and diagnostics; use the data-aware path or repair before a
  new scenario.
- **Product defect:** patch the owner, obtain a new target artifact, and rerun affected rows.
- **Environmental transient:** do not add blind retry. Fix the environment and restart from a fresh
  baseline.

### 7.8 Exact-no-op mutation

Any backup, process restart, pointer write, file rewrite, migration, fence, permit, journal, or product
row change is a test failure and likely a product defect. Do not redefine no-op to include harmless
mutation.

### 7.9 Restart failure

- Preserve systemd properties, process/cgroup identities, bounded logs, listener state, and fence/
  permit state.
- Do not force start by deleting a fence or bypassing `ExecStartPre`.
- Recreate from a fresh accepted baseline or target after diagnosis.
- A Docker daemon or host failure is classified separately from a product service failure.

### 7.10 Restore failure

- Never overwrite the source database.
- Retain the original verified backup and rejected restore diagnostics.
- Drop only the operation-owned failed target after evidence capture.
- Retry only into a new empty target after the cause is corrected.
- Do not call a partial schema or successful command exit recovered.

### 7.11 Missed interruption window

If the fence/state/migration predicates are not simultaneously and unambiguously observed before the
updater is killed, mark the attempt invalid, clean the project, and rerun from a fresh baseline. Do not
add a production test hook merely to make the race easy.

### 7.12 Recovery failure

- Preserve fence, journal, both releases, backup, rollback point, service stop, and first causal error.
- Do not delete the fence or write a start permit manually.
- A changed or unreadable migration ledger remains restore-required.
- Retry only after exact state identity is understood and the packaged recovery prerequisites are
  restored.

### 7.13 Cleanup or evidence failure

Behavioral success plus cleanup failure is `FAILED`. Secret-scan failure prevents ordinary evidence
retention; retain only a constant safe marker and necessary non-sensitive cleanup result. Never delete
an unrelated Docker object to make cleanup green.
