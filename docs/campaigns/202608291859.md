## 5. Authority model and target invariants

### 5.1 Authorities

For this campaign:

- **Product semantics:** current Rust/JVM source, schema migrations, protocol contracts, and current
  owner documents at the exact final commit.
- **Release inventory:** the independently authored release-artifact owner and the generated manifest
  verified against it.
- **Source identity:** the exact clean Git commit object imported from an explicitly verified
  self-contained closure.
- **Installed release identity:** root-owned versioned release directory, manifest/sidecar, embedded
  binary and jar identities, and the atomically selected current pointer.
- **Update operation state:** one root-owned global lock plus the durable fence and deployment journal
  owned by the packaged coordinator.
- **Application durable state:** PostgreSQL, with committed migrations and transactionally controlled
  operation facts.
- **Observed runtime state:** systemd unit/cgroup, verified owned processes, listeners, local
  Minecraft proxy response, database connection, heartbeats, and registrations.
- **External host state:** the live authoritative container manager, host snapshots, proxy devices,
  and traffic routes. In-container code may record a host snapshot label but may not claim it
  observed the host snapshot.
- **Evidence:** exact commands, exit status, bounded redacted logs, manifests, checksums, process and
  listener observations, database queries, protocol-client results, and remote workflow conclusion
  bound to the final commit.

No document or receipt may make a lower authority override a higher one.

### 5.2 Reader, writer, and effect boundaries

- Only the packaged privileged updater may coordinate release adoption and recovery.
- Only one updater/recovery operation may hold the global deployment lock.
- Root owns release roots, manifests, update state, fence, and privileged systemd files.
- The service account owns only the runtime paths it requires; it must not be able to modify release
  identity, deployment state, privileged units, credentials outside its scope, or the updater.
- The daemon owns policy, desired state, authorization, durable operations, and runtime
  reconciliation.
- PostgreSQL owns durable product facts but never substitutes for live JVM truth.
- systemd owns the supported service lifecycle.
- Velocity owns proxy command registration and actual player connection requests.
- backend plugins do not create proxy sessions or become deployment authorities.
- the container manager owns container lifecycle, resources, snapshot state, and host network
  devices.
- remote CI proves only the source/release/test boundary it actually executes.

### 5.3 Release and source invariants

The final release must:

- be built from a clean exact commit after all source changes;
- contain no dependency on the caller's ambient source tree or build outputs;
- include an importable source object/ref closure sufficient for the repository's exact identity
  checks;
- make the exported ref and the importer's expected ref explicit and consistent;
- fail when required Git objects are absent;
- carry exact manifest and sidecar identity;
- contain the exact artifact set derived independently from the inventory owner;
- bind source, binaries, jars, schema/configuration identity, operational tools, systemd owners, and
  checksums as current design requires;
- contain no secrets, source checkout, build cache, private evidence, worlds, database dump, or
  unowned jar;
- use immutable upstream identities and verified digests;
- refuse a mutable or already-conflicting versioned target;
- be transferred and verified separately from the operator-supplied manifest digest;
- retain enough previous exact release state for safe recovery.

A mutable channel may help resolve an artifact but is never installed identity.

### 5.4 Update invariants

Before any service stop or data mutation, the updater must verify:

- effective root authority and trusted command paths;
- target release ownership, ancestry, modes, inventory, digest, and embedded identity;
- exact current release and `--from-commit`;
- existing healthy fixed topology and required credentials;
- database reachability and migration marker;
- existing EULA acceptance without creating it;
- private writable paths and absence of path traversal or symlink substitution;
- one global lock;
- a fresh non-existing backup destination;
- a valid, independently inspectable PostgreSQL backup;
- rollback identity and explicit host snapshot assertion;
- no unsafe schema/binary rollback mismatch known at preflight.

A failure before durable fencing must leave current release, processes, plugins, unit, pointer,
database, and public/private boundaries unchanged.

### 5.5 Exact no-op invariants

For an identical target release:

- return an explicit no-op result;
- do not create a backup;
- do not create a fence, permit, or deployment journal;
- do not stop or restart the service;
- do not run migrations;
- do not republish artifacts, plugins, unit files, or the current pointer;
- do not change database product state;
- do not change process identities;
- do not require a host snapshot;
- clean only stale non-durable state that is unambiguously safe and record such cleanup separately
  from the no-op operation.

Codex must establish a before/after oracle for these effects instead of relying only on the updater's
reported result.

### 5.6 Fencing, interruption, and recovery invariants

- The durable fence is installed before runtime publication and before the old service can be stopped
  into an ambiguous state.
- A container or service restart while the fence is present must not automatically launch either
  release.
- A bounded root-owned runtime permit may authorize only the coordinator's one verification start
  and must be atomically consumed.
- Automatic restart after permit consumption remains blocked while the fence exists.
- The deployment journal is private, exact, durable, and sufficient for the packaged recovery tool.
- Recovery begins by stopping and classifying any surviving service-account process.
- When the migration ledger remains exactly compatible, recovery restores the complete old unit,
  current pointer, plugin bytes, and release identity, then starts and independently verifies the
  old release.
- When the migration ledger changed or is unreadable, binary-only rollback is forbidden. The service
  remains fenced and diagnostics identify the verified database backup and external snapshot needed
  for data-aware recovery.
- Success removes fence and permit only after the accepted target is independently healthy.
- Failure never deletes the only verified old or new tree.

### 5.7 Database and backup invariants

- PostgreSQL is the product durable store.
- A pre-update dump must be transaction-consistent, private, bound to server/schema/migration/source
  identity, checksummed, and independently listable.
- Existing backup destinations are never overwritten.
- Partial backup output is removed by its creator.
- Backup creation and isolated restore are separate evidence tiers.
- The restore target must be fresh and must not overwrite the source database.
- Restore verification includes checksum, metadata, tool/server compatibility, migration marker,
  expected schema/data query, and actual daemon boot or the strongest current owner-defined
  application check.
- The failed or source database remains retained until the restored target is accepted.
- Secrets and database URLs never appear in tracked files, retained public evidence, or the handoff.

### 5.8 Process and readiness invariants

- PID alone is not process ownership; verify durable identity, process group/cgroup, executable, and
  current observation as current code requires.
- Desired state, durable operation state, process existence, component readiness, backend
  joinability, proxy reachability, and real-player acceptance are distinct.
- Spawn and port bind are not accepted Minecraft readiness.
- Successful update requires systemd active, expected owned processes, exact release identities,
  expected topology, fresh registrations/heartbeats where retained, a no-op post-start plan, and a
  real local proxy protocol response.
- Stop and rollback operate only on verified owned process groups.
- Timeouts, cancellation, and retries are bounded and preserve the durable operation truth.
- Crash-loop or repeated-start behavior remains visible and bounded; do not hide it with retries.

### 5.9 Network and host invariants

- Use one authoritative Incus or LXD manager discovered live.
- The disposable target is unprivileged and has explicit resources based on current capacity.
- It has no public proxy device and receives no production traffic.
- Daemon HTTP, PostgreSQL, and backend listeners remain private.
- Only the intended Velocity listener may be externally reachable in supported production, but this
  campaign does not alter production exposure.
- Do not add privileged mode, host networking, broad host mounts, container-manager sockets, Docker
  sockets, nesting, or bridge bypass for convenience.
- Verify unrelated host services and resources remain unchanged.
- Destroy or retain the disposable target only according to explicit ownership and evidence needs;
  never leave an ambiguous live clone with production credentials or public exposure.

## 8. Failure, interruption, and recovery contract

For each material failure, Codex must verify or document all seven fields: visible result, durable
state, retry semantics, cleanup owner, diagnostics, recovery, and stop condition.

### 8.1 Clean verification failure

- **Visible result:** nonzero workflow/check with the first real failing owner named.
- **Durable state:** no accepted release.
- **Retry:** only after source or environmental prerequisite changes.
- **Cleanup:** Compose/project owner removes containers, volumes, networks, and private temporary
  source/release directories.
- **Diagnostics:** bounded, redacted, retains original exit status.
- **Recovery:** repair root cause and rerun fresh.
- **Stop:** never upload or label failed evidence as accepted.

### 8.2 Incomplete or wrong source closure

- **Visible result:** bundle verification/import or exact commit comparison fails.
- **Durable state:** no release publication or install.
- **Retry:** create a complete explicit closure from the exact commit.
- **Cleanup:** remove private partial import/output only after identity-safe cleanup.
- **Diagnostics:** expected/observed commit and advertised refs, no secrets.
- **Recovery:** none beyond rebuilding exact closure.
- **Stop:** do not weaken exact source identity.

### 8.3 Preflight trust, digest, identity, or backup failure

- **Visible result:** nonzero before mutation.
- **Durable state:** baseline release, service, database, plugins, unit, pointer, and network unchanged.
- **Retry:** correct the input or prerequisite, then start a new operation under the global lock.
- **Cleanup:** updater removes only owned partial backup/temp state.
- **Diagnostics:** identify the failed invariant without credential values.
- **Recovery:** not required because no effect boundary was crossed.
- **Stop:** any service or data mutation makes the case a defect.

### 8.4 Lock conflict

- **Visible result:** one contender fails promptly and truthfully.
- **Durable state:** only the lock holder may own operation state.
- **Retry:** after the first operation reaches a classified terminal or recoverable state.
- **Cleanup:** no second-operation state.
- **Diagnostics:** busy operation without leaking private paths unnecessarily.
- **Recovery:** inspect the first operation, not force-unlock blindly.
- **Stop:** never run two coordinators concurrently.

### 8.5 Failure before migration change

- **Visible result:** failed update plus rollback/recovery classification.
- **Durable state:** either an active durable fence and exact journal, or the fully restored old
  release; never a mixed selected release.
- **Retry:** only after recovery reaches a verified terminal state.
- **Cleanup:** packaged coordinator owns permit, fence, journal, staged publication, and old/new tree
  decisions.
- **Diagnostics:** exact from/to identities, state, backup, and recovery command.
- **Recovery:** restore old unit/pointer/plugins, start and verify old release.
- **Stop:** do not remove fence before independent old-release acceptance.

### 8.6 Migration changed or unreadable

- **Visible result:** binary rollback refused; service remains fenced.
- **Durable state:** failed database retained, verified backup and external snapshot identified, old
  and new releases retained.
- **Retry:** only through data-aware restore and matching release.
- **Cleanup:** no destructive cleanup of the only data/release copy.
- **Diagnostics:** migration marker status and exact recovery boundary, no database URL.
- **Recovery:** isolated restore, acceptance, then atomic configuration/release selection.
- **Stop:** never repoint only the binary.

### 8.7 Interruption or container restart while fenced

- **Visible result:** ordinary systemd start blocked.
- **Durable state:** fence and journal survive; runtime permit is absent or bounded and consumed.
- **Retry:** run exact packaged `recover` or resume only if current design proves it safe.
- **Cleanup:** recovery owner.
- **Diagnostics:** classified journal/fence state.
- **Recovery:** Section 6, Slice 7.
- **Stop:** manual deletion of fence/journal is forbidden as a shortcut.

### 8.8 Restore failure

- **Visible result:** nonzero restore/boot acceptance.
- **Durable state:** source database and backup retained; failed fresh target isolated.
- **Retry:** after correcting tool/version/input/environment issue.
- **Cleanup:** drop only the failed fresh target after evidence retention.
- **Diagnostics:** checksum/version/schema/migration/boot failure, no credentials.
- **Recovery:** retry into another fresh target.
- **Stop:** never overwrite the source or call dump creation recoverability.

### 15.7 Failures and limits

- preexisting failures;
- failures discovered and repaired;
- failed experiments;
- skipped, blocked, and not-run evidence;
- production and real-player boundaries explicitly not observed;
- remaining risks;
- unsupported clean-install boundary;
- one next executable action, or a precise statement that the campaign objective is closed.

## 16. Stopping rule

Stop successfully only when:

- the exact final commit passes every required remote verification gate;
- its exact release is independently source-closed and artifact-verified;
- the disposable existing-deployment changed update is accepted;
- exact no-op is independently accepted;
- service and container restart adoption are accepted;
- the updater-created PostgreSQL backup is independently restored;
- controlled post-fence interruption and packaged recovery return to one verified release;
- no stale authority, fence, permit, journal, partial publication, fallback, or private/public
  boundary regression remains;
- documentation and the active ledger describe the evidence honestly;
- the integration path and worktree are clean or precisely classified;
- production, publication, clean installation, and real-player acceptance were not claimed.

A green local suite alone, a built archive alone, a successful preflight alone, a process spawn, a
socket, a proxy ping, a historical deployment record, or a blocked guarded lane does not satisfy this
campaign.
