## 1. Mission

### 1.1 Primary objective

For one exact final commit, make the release accepted by lkjmc's pinned verification workflow
available as one canonical, permission-preserving, content-addressed transport archive, retain that
archive as a GitHub Actions artifact, and independently download and reverify it without rebuilding
Rust or JVM outputs.

The observable final state is:

> An operator can identify one successful `main` workflow run, retrieve the exact canonical release
> archive produced only after the workflow's two release roots agree, verify its separately reported
> archive and manifest digests, safely reconstruct the exact release root with the expected modes and
> embedded source identity, and hand those bytes to the existing packaged updater later without a
> source checkout or build toolchain in the target runtime.

This campaign closes **release handoff**, not deployment. It must not claim that the archive was
installed, that an update or no-op ran, that systemd or a container restarted, that PostgreSQL was
restored, that a listener was reachable, that a player logged in, or that production changed.

### 1.2 Affected outcome

The affected party is the lkjmc operator and the next Codex session responsible for the disposable
update matrix.

At the inspected revision, release construction is strong but ephemeral:

- the exact `Verify` run for the inspected commit is green;
- the workflow builds two release roots inside one pinned verifier image and compares their path,
  type, mode, size, and digest closure;
- the workflow retains bounded operations evidence, the generated release manifest, and its sidecar;
- the retained artifact does **not** contain the release directory or a transport archive containing
  the release binaries, jars, privileged tools, and systemd owners;
- the release build root disappears with the hosted runner;
- the current known Codex workspace could not create the required nested containers, and no
  authorized Incus/LXD manager or retained deployment lineage was available;
- a later live campaign would therefore need to reconstruct the release in another compatible build
  environment before it could even begin operator adoption proof.

A manifest proves what bytes were built. It is not the bytes themselves. A log, provenance record,
checksum sidecar, or successful workflow conclusion is not a retrievable release artifact. This
campaign makes the distinction executable.

## 6. Authority model and target design

### 6.1 Semantic and generated authorities

- `config/release-artifacts.json` remains the independent semantic owner of installed release
  artifacts.
- `scripts/build-release.sh` remains the release-root construction owner.
- `scripts/artifact-manifest.py` generates the manifest from the independent inventory and exact
  release root.
- `scripts/verify-artifact-manifest.py` remains the independent manifest/sidecar verifier.
- `scripts/compare-release-roots.py` remains the byte-and-mode equality oracle for the two fresh
  builds.
- The new narrow archive tool is the sole owner of transport archive creation, archive validation,
  and safe extraction semantics.
- The generated handoff descriptor owns the association among final source commit, product version,
  archive identity, manifest identity, workflow identity, and outer artifact name.
- `.github/workflows/verify.yml` owns orchestration, not artifact semantics.
- GitHub Actions storage retains bytes but is not semantic or installed identity.
- `docs/work/active.md` owns current resumable status, not release bytes.

### 6.2 Release root versus transport archive

The release root is the installed-content candidate. The transport archive is a deterministic carrier
around that root.

The archive must not:

- add installed files;
- remove installed files;
- rewrite file content;
- invent executable modes;
- become a second manifest;
- contain the source bundle, checkout, caches, evidence logs, database data, worlds, or secrets;
- change updater or installation semantics.

A verified extraction must reconstruct a release root that the current independent manifest and
identity verifiers accept.

### 6.3 Canonical archive construction

The archive tool must:

1. require an existing verified release root and a nonexisting output path;
2. obtain the exact source commit and canonical product version from current authorities;
3. open and traverse the release root through the repository's descriptor-safe no-follow owner;
4. reject root replacement, device crossing, unreadable paths, symlinks, special files, unstable
   identity, depth/count/size overflow, or any member outside the expected release closure;
5. require exact equality with the current independently derived release-root closure before writing;
6. write to a private temporary file owned by the current operation;
7. emit one explicit top-level directory and every contained directory and regular file;
8. use deterministic path order and normalized header metadata defined in Section 5.3;
9. copy each file through an already validated descriptor and verify size/identity while reading;
10. flush and fsync the archive before publication;
11. compute SHA-256 and size from the final closed archive;
12. atomically publish only to a nonexisting final path;
13. remove only its own temporary output after failure, using retained identity to avoid deleting a
    replacement;
14. emit a machine-readable result sufficient to build the handoff descriptor;
15. produce the same bytes on a second pack of the same accepted root.

Do not use wall-clock time, host uid/gid, host path, random ordering, locale, ambient umask, or runner
identity in canonical archive bytes.

### 6.4 Canonical handoff descriptor

Use one canonical UTF-8 JSON object with sorted keys, deterministic separators, and a terminal newline.
At minimum it records:

- schema version;
- repository identity;
- source commit;
- canonical product version;
- archive format;
- archive filename;
- archive byte size;
- archive SHA-256;
- release-manifest SHA-256;
- release-manifest-sidecar SHA-256;
- exact top-level archive directory;
- exact outer artifact name;
- workflow event name;
- workflow ref;
- workflow run ID;
- workflow run attempt;
- producer job identity;
- statement that the outer artifact is transport and the inner archive is the canonical payload.

Do not put credentials, actor email, host paths, runner names, private infrastructure identifiers, or
mutable download URLs in the descriptor.

The archive digest sidecar uses one strict line containing the lowercase SHA-256, two spaces, and the
exact archive filename. The consumer must parse it strictly rather than split arbitrary text.

### 6.5 Outer artifact closure

The promoted release artifact contains exactly:

1. the canonical release tar archive;
2. its strict SHA-256 sidecar;
3. the canonical handoff descriptor.

No logs, build outputs outside the release root, source bundle, image tar, database dump, world, or
unindexed file belongs in this artifact.

The artifact name must include the full source commit. The workflow must reject a collision or an
unexpected existing output rather than overwrite it. Retention must be explicit and documented. The
final handoff must state that retention is finite.

### 6.6 Independent consumer

The consumer job must be a separate job with an explicit dependency on the successful producing job.
It must:

1. run for the same workflow commit and attempt;
2. download the exact artifact by the producer's exact output identity;
3. require the exact three-file outer closure;

### 6.7 Artifact-service and expiration semantics

## 9. Failure, interruption, retry, and recovery semantics

### 9.1 Packaging failures

For unreadable input, unstable identity, unexpected member, invalid mode, output collision, disk
exhaustion, write error, fsync error, digest error, or interruption:

- exit nonzero;
- do not publish a final archive, sidecar, or descriptor;
- remove only operation-owned temporary state whose identity still matches;
- preserve the accepted input release root;
- emit a bounded diagnostic naming the failed stage and nonsensitive path role;
- allow retry with a new nonexisting output after the cause is corrected.

A partial archive is never resumable or accepted.

### 9.2 Verification and extraction failures

For malformed headers, wrong normalized metadata, duplicate names, traversal, links, special files,
truncation, checksum mismatch, descriptor mismatch, sidecar mismatch, manifest mismatch, embedded
identity mismatch, extraction conflict, or disk exhaustion:

- exit nonzero before publishing an extracted release root;
- retain no accepted partial target;
- do not execute binaries from an unverified archive;
- clean only operation-owned temporary extraction state;
- preserve the downloaded archive for bounded diagnosis when safe;
- require a fresh verification attempt after correction or redownload.

### 9.3 Workflow failures

- A failed build, comparison, identity check, manifest check, secret scan, evidence preparation,
  cleanup, packaging, upload, download, or consumer verification fails the required workflow.
- A cancelled or superseded workflow is not acceptance.
- A scan failure may upload only a constant safe failure marker; it must not upload rejected release
  or evidence bytes.
- An upload that succeeds before a later required failure remains an unaccepted artifact. The final
  handoff must not advertise it.
- A consumer retry is acceptable only as a new explicit job/run attempt whose identity is recorded;
  hidden command retries are forbidden.
- A missing or expired artifact is `BLOCKED` or `FAILED` availability, not proof that historical
  bytes changed.

### 9.4 Idempotency

- Repacking the same accepted root with the same canonical owner yields identical bytes and digest.
- Reverification is read-only except private temporary extraction.
- The packer refuses to overwrite an existing output.
- Workflow artifact names are exact to one commit/run context; collisions fail.
- Post-run download does not mutate repository, release, service, database, or host state.

### 9.5 Stop conditions

Stop and classify rather than weaken acceptance when:

- the current action platform cannot retain the archive safely;
- the release root contains unsupported file semantics that cannot be represented without changing
  installed behavior;
- independent consumer verification requires a rebuild;
- artifact storage cannot be accessed with current authorization;
- a later checkout already establishes a stronger canonical handoff that would make this path
  duplicate;
- the exact final workflow cannot complete;
- source changes reveal that host mutation is required to prove archive identity.
