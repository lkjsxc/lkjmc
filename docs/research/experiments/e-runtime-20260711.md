# Experiment E-RUNTIME: lifecycle coordinators

## Purpose

Compare research-only lifecycle coordination around one local-process and
Kubernetes-planner slice. This experiment cannot select or change a daemon
runtime, command, adapter, schema, or state claim.

## Observed problem

The daemon currently puts every `RuntimeAdapter` call behind one `Arc<Mutex>`
in `crates/lkjmc-daemon/src/app.rs` and `support/instance_helpers.rs`. Local
recovery fences an unverifiable live PID, while Kubernetes planning is pure and
live cluster verification is opt-in. Neither fact proves per-instance
serialization or cross-daemon fencing.

## Hypothesis

A keyed guard and a per-instance mailbox can serialize one instance while a
hung different instance proceeds. PostgreSQL advisory ownership plus a durable
generation can reject a stale cross-daemon effect. No candidate may turn an
effect, an early exit, or a missing observation into successful health.

## Real boundaries

- The harness creates and terminates real local child process groups.
- It runs the existing local-runtime safety tests and Kubernetes planner tests.
- With Compose available, it holds real PostgreSQL advisory locks in distinct
  `psql` sessions and writes only an experiment-owned fence table.
- It does not access a cluster, alter product tables, or register a product path.

## Candidate variants

- `keyed`: in-process lock per instance key.
- `mailbox`: in-process FIFO worker per instance key.
- `advisory`: PostgreSQL session advisory lock with a persisted generation.

## Required combinations

The harness runs two explicitly bounded executor sizes with keyed and mailbox
coordination, each with an fsync-backed research journal. Every peer is
submitted through the selected executor; a hung task signals only after it has
entered coordinated work. It also records bounded/keyed, async/keyed,
bounded/journal, async/journal, and async/journal/mailbox controls.

## Workload and faults

A fixed seed `20260711` drives one coordinated hung key with one unrelated
executor-dispatched key, simultaneous same-key starts, effect failure,
observation failure, and shutdown. A disposable coordinator process starts a
child, fsyncs its PID and generation, then is killed. A distinct recovery
process reads that journal, fences the stale process group, advances the
persisted generation, reacquires once, and proves cleanup. PostgreSQL repeats a
real session-coordinator crash and connection-loss probe: a new session must
reacquire its advisory lock and generation while a stale generation is rejected.
Each local and PostgreSQL candidate runs three repetitions.

## Measurements

Correctness requires one same-key start effect, unrelated-key completion while
the coordinated hung key remains held, no successful failed or unobserved
effect, and a fenced stale PID before generation reacquisition. Every started
PID is retained until termination; shutdown passes only with an explicit
zero-survivor record. The harness records elapsed milliseconds, effect counts,
journal event counts, exit states, coordinator crash/recovery facts, and
PostgreSQL lock and connection-loss outcomes. Any unproved probe is
`BLOCKED` or partial, never `PASS`.
