# E-DATA durable-workflow experiment

## Purpose

Compare private-schema data candidates against an actual disposable current
profile and transfer-audit slice. This research changes no product schema,
store, adapter, controller, or player-facing claim.

## Status

experiment

## Baseline and question

This evaluates `DW-TRANSFER-FLOW`, `DW-PROFILE-FORMAT`, `DW-DELIVERY-FLOW`,
`DW-REVISION`, `DW-NOTIFY`, `DW-FENCE`, and `DW-LEDGER-INVARIANT`. The current
slice has immutable `player_profile_snapshots`, leases, `player.snapshot`,
`player.restore`, and `player.transfer.saved`; the last command writes only an
audit event. Paper/Folia and Velocity transfer adapters remain withdrawn.

The question is whether a bounded typed envelope, a correlation-keyed fence,
and durable revision history are useful future inputs. It does not ask whether
the candidate has delivered an item or moved a player.

## Representative slice and invariants

The harness starts the real daemon against disposable Compose PostgreSQL, then
uses the real CLI to snapshot and restore one profile. It calls the real UNIX
command endpoint for `player.transfer.saved` and checks the resulting audit
row. It proves two durable revisions and an audit acknowledgement only; it
cannot prove plugin save/load, session attestation, inventory receipt,
connection result, or arrival.

- Candidates use one randomly named private schema; no tracked migration or
  product table contains candidate fields.
- The current snapshot/restore rows retain two revisions for the fixed player.
- A six-second `ACCESS EXCLUSIVE` profile-table delay must cause the current
  five-second database lock timeout; no post-delay retry is interpreted as
  recovery.
- A six-second hold of the actual migration advisory lock must make one CLI
  migration attempt time out. The separately logged post-release migration is
  setup continuation, not evidence that a retry resolves a lock failure.
- The candidate dump contains both `public` and the private schema. Reset,
  explicit drop of both schemas, `pg_restore`, status, and private-table checks
  constitute the disposable cutover drill.

## Candidate comparisons

The private schema contrasts opaque bytes with typed JSON/checksum validation,
weak duplicate delivery rows with a fenced correlation record, and a private
revision feed. It also checks rollback, reclaimed stale ownership, and the
current immutable points ledger after deterministic spend/refund. These are
candidate-table observations, not a profile-transfer claim.

## Blocked combination

No current workflow joins the snapshot revision, a durable transfer journal,
and a real plugin acknowledgement. `player.transfer.saved` has no revision or
correlation input and writes an audit event; `lkjmc_store::command::insert_requested`
is not wired by the daemon; Java transfer bridges are withdrawn. The harness
records this as `workflow-journal-plugin-ack: BLOCKED`, not as a pass.

## Environment and rerun

Allowed repository writes are `docs/research/**`; raw output is a bounded,
owned ignored `/tmp` root. Docker, Compose, `postgres:16-alpine`, locked Rust
dependencies, and a free loopback port are prerequisites.

```sh
python3 "$REPO/docs/research/experiments/e-data-20260711.py" \
  --output /tmp/lkjmc-e-data-correction
```

The harness retains per-command exit, capped log, log hash, classification, and
archive hash in `result.json`, then removes the Compose containers and volumes.
A missing prerequisite or failed probe is failure or block, never success.
