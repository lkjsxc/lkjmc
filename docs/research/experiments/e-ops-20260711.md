# E-OPS reproducibility hypothesis

## Purpose

Compare disposable operational evidence paths without registering an operation,
release, or external-runtime success in the product.

## Catalog and baseline

This tests `OP-CLEAN-COMPOSE`, `OP-ROOTLESS-LAB`, `OP-RESTORE-DRILL`,
`OP-KUBE-LAB`, `OP-SYSTEMD-HARDEN`, `OP-ARTIFACT-MANIFEST`, `OP-SIGN`,
`OP-TOOLCHAIN-PIN`, `OP-SKIP-EVIDENCE`, and `OP-FAULT-LAB` from
[operations ideas](../ideas/operations.md). The base is
`d20e5e532db9d3a5577f567dd6a5a24fdc51eea1`.

## Hypothesis and slice

A rebuilt, uniquely named Compose verify run can provide deterministic
PostgreSQL and verification evidence. A separate disposable restore database
can be dumped, restored, migrated, and queried through a daemon boot. A
research-only harness will retain redacted command output, exit codes,
checksums, and cleanup results under an owned ignored temporary directory.

Rootless Docker, a Kubernetes cluster, a signing key, and a systemd service
manager are independent external boundaries. Each receives an actual command;
absence or rejection is external proof pending, not a passing result.

## Invariants

- Do not change controller state, owner contracts, product adapters, or CI.
- Do not send generated tokens, database URLs, dumps, or raw logs to Git.
- Use unique Compose projects and only the Compose PostgreSQL database.
- Do not treat `config`, client creation, or an ignored command failure as a
  runtime success.
- Stop processes and remove only the uniquely named Compose project, volumes,
  and owned temporary root.

## Variants and workload

The candidates are: rebuilt Compose verify; a Docker rootless-context Compose
attempt; a dump/restore/daemon-start drill; guarded Kubernetes smoke; an
isolated `systemd-run --user` sandbox; and static artifact/toolchain/skip/fault
inspection. One run uses seed `20260711`, no synthetic player data, and a
single Compose PostgreSQL service. The restore drill starts a real daemon and
queries `doctor`; it does not start a Minecraft adapter.

The clean Compose candidate repeats the full verify command once after a
no-cache image build. The restore candidate repeats only once because it
creates and destroys a database. The fault candidate runs the test-only fault
harness once. No performance, player-capacity, release-signing, or cluster
claim is measured.

## Measurements and faults

Record command exit code, elapsed time, image/config digest, component versions,
final nested `ran` and `skipped` fields, daemon socket response, and cleanup
exit. The negative cases are unavailable rootless context, absent Kubernetes
prerequisites, absent signing key, unavailable systemd manager, and fault
markers in release artifacts. Redaction scans retained evidence for generated
secrets and passwords.

## Worktree and reruns

Only `docs/research/**` and an isolated disposable harness under
`docs/research/runs/` may change. Raw artifacts belong below
`/tmp/lkjmc-e-ops-*`. The later run record supplies the exact portable commands
for each available and pending boundary. A separate decision records only
research disposition; adoption requires a later task.
