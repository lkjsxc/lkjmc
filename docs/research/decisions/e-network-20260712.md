# E-NETWORK research decision

## Purpose

Record a non-adoption disposition for the declarative network comparison.

## Disposition

`reject` product adoption now. The JSON document, compiler, local adapter, and
Kubernetes manifest adapter remain isolated research evidence. This registers no
controller, daemon command, runtime, migration, asset download, plugin install,
or state capability.

## Evidence

The [hypothesis](../experiments/e-network-20260712.md) fixed the document and
workload before the harness. The [run](../runs/e-network-20260712.md) records
real owned local child starts, reapply, optional-backend change, rollback,
removal, post-start failure cleanup, unsupported policy rejection, six rendered
Kubernetes objects, and four live children from the imperative comparison.

The baseline document compiled to two resources; enabling `events` compiled to
three. The second declarative apply started none. The removal path stopped
`events` and re-rendered proxy because its routing data changed. The controlled
failure stopped only the newly started `events` child while base resources
remained observed. These are bounded harness facts, not Minecraft readiness,
asset integrity, player routing, or durable reconciliation facts.

Kubernetes remains external proof pending. The actual attempt was `kubectl
version --client --output=yaml`, which exited 127 because the executable was
absent. No cluster object was applied or observed. Treating the manifest output
or absent client as Kubernetes support would be false.

## Why no adoption

The candidate has no PostgreSQL desired-state record, ownership fence, durable
operation journal, authenticated operator input, asset verification, plugin
trust, port binding, Minecraft readiness, daemon restart recovery, or Java
proxy registration. Its local children are deliberately generic and its
imperative comparison is not the daemon bootstrap path. A pure plan and a
local cleanup result cannot bridge these boundaries.

## Reconsideration

A separate task may reconsider only after an owner-approved JSON contract,
durable desired/observed state and failure semantics, product adapter tests, and
an attested local Minecraft slice. Kubernetes additionally needs a successful
client capability attempt, authorized disposable namespace, owned-object apply,
observe, reapply, failure, deletion, and rollback evidence. Any selection must
update owner and state documentation in that later task; this decision does not.
