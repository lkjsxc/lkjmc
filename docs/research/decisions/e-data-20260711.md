# E-DATA durable-workflow decision

## Purpose

Interpret corrected research evidence without adopting or registering a schema,
workflow, controller, Java adapter, transfer, or delivery behavior.

## Status and disposition

research only; no combined candidate is retained for adoption.

Keep the typed-envelope, fence, and revision-feed observations as separate
future hypotheses. Do not combine them into a profile/player-transfer proposal:
the current workflow/journal/plugin-acknowledgement combination is blocked, and
the current transfer acknowledgement is only an audit row. Opaque profile
bytes, duplicate correlation rows, and notification-only freshness remain
rejected as candidate sources of truth. This changes no product behavior.

## Evidence

- Corrected hypothesis: [E-DATA experiment](../experiments/e-data-20260711.md).
- Corrected observation: [E-DATA run](../runs/e-data-20260711.md), including
  source/result/archive hashes, exact lock-timeout text, per-attempt exits,
  capped-log hashes, classifications, and the private-schema cutover drill.
- Current boundary: [player profile](../../product/sync/player-profile.md) and
  [transfer safety](../../product/sync/transfer-safety.md).
- Source inspection: `crates/lkjmc-daemon/src/commands/player.rs`,
  `crates/lkjmc-store/src/command.rs`, and the withdrawn Java boundary.

## What the run establishes

The actual disposable daemon/CLI slice stored and restored two current profile
revisions. A real local command endpoint call recorded `player.transfer.saved`
in `audit_events`. A current profile-table lock caused the documented database
lock timeout without adding a third snapshot. The private candidate schema
survived a full dump, reset, explicit public recreation/private drop, restore,
and status check. These are bounded database observations.

The intentional migration-lock failure confirms the harness captures a real
PostgreSQL timeout. Its later post-release migration success is not evidence
that retry resolves the old unretained Compose incident, or that retry is a
safe production policy.

## What remains unproved

No evidence joins an authenticated player/session, exact snapshot revision,
durable transfer journal correlation, plugin save/load acknowledgement, target
connection result, or inventory receipt. `player.transfer.saved` accepts no
revision or correlation and writes only audit data. The store command-journal
insert helper is not wired by the daemon. Java and proxy transfer adapters stay
withdrawn, so the run cannot establish a workflow combination or a player move.

Capacity, retention, authorization, scheduler impact, notification pressure,
and compensation ownership also remain unmeasured. The candidate fence is not
an item-delivery proof.

## Reconsideration

A separate proposal needs trusted identity/session attestation; a real
nonblocking Java save/load/transfer adapter; a revision-and-correlation-bound
journal; plugin acknowledgement and connection-result evidence; retention and
authorization rules; and faults against the current atomic economy. It must
repeat the private cutover drill and record raw failure provenance before any
adoption task can be considered.

Until then, this material remains under `docs/research/**`; no owner/state
contract or controller ledger is updated. The next executable step is an
isolated adapter experiment that proves the blocked combination with a real
authenticated test player, or records its missing prerequisite as blocked.
