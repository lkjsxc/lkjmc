# E-JVM isolated adapter decision

## Purpose

Interpret E-JVM evidence without selecting, registering, or restoring a Java
adapter, command, credential path, sync surface, topology action, or state
claim.

## Disposition

`EXTERNAL PROOF PENDING; retain only as post-synthesis research input.`

The current withdrawn Java boundary is a constraint, not a candidate to work
around. There is no pre-synthesis adoption and no owner or state-document
change.

## Evidence and comparison

- Scope and limits: [E-JVM hypothesis](../experiments/e-jvm-20260711.md).
- Execution: [E-JVM run](../runs/e-jvm-20260711.md).
- Reproducible harness: `e15c264d15c3dab2d8f47ce68d6bc797e680e83c`.
- Independent reproduction and review: pending.

The pure revision comparison showed why any later synthesis must compare a
durable revision repair with treating an SSE/push notification as complete state: the dropped `3` left the event-only
row nonconvergent, while the repair row reached `4`. Adaptive snapshots and
bounded waits also reached the current revision, but the harness establishes no
wire cost, backoff policy, stream liveness, or server load. Two failed retries
ended offline, so a later candidate must retain a finite retry budget and never
invent freshness.

The future fence demonstrated a submit-and-return shape with a held worker. The
virtual-worker row began eight held tasks where the two-worker fixed pool began
two. This is not a recommendation to use virtual threads in a plugin or daemon:
there is no database, network, cancellation, queue pressure, memory, or
scheduler-runtime measurement. The typed dispatcher correctly rejected a
withdrawn effect, which is a useful fail-closed invariant only.

Static topology lookup did not discover a server, register one, transfer a
player, or establish a proxy connection. Correlated workflow outcomes preserved
one test ID and denied every missing auth or attestation combination. The fully
present combination remained `RESEARCH_ONLY`; it did not authorize an effect or
claim arrival.

## Required conditions before reconsideration

A separate, reviewed synthesis may revisit these algorithm results only after
trusted player identity/session attestation exists. It must define bounded
credentials, cancellation, overload, durable revision reads, reconnect policy,
and correlated observed outcomes; then use a real disposable Paper/Folia and
Velocity topology with no scheduler-thread blocking. It must exercise dropped
and reordered events, expiry/revocation, restart, topology loss, and actual
connection outcome. New owner contracts, implementation work, containment, and
live proof are required before any adoption claim.

Until then, retain the harness and raw replay index as research evidence. The
next executable step is an independent replay of the run command, followed by
review against the withdrawal constraints.
